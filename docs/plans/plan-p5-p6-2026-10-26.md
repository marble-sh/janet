# P5/P6 implementation brief — process memory and meta-loop

**Status:** ACCEPTED (2026-10-26) — two 10-generation confirmations, checkpoint between
**Scope:** P5 process memory and P6 meta-loop for Janet
**Hardware contract:** 8 CPU cores soft, 14 GiB RAM soft, 3.99 GiB VRAM soft,
16 GiB disk, 300 s/hour spike; one local 7B q4 policy model and one 3B q4 judge,
one loaded model at a time; no weight training, no fine-tuning, no runtime
network.
**Evidence base:** 223-paper audit in
`docs/state/reference-download-2026-10-26/validation-report.md`; 23 A-tier
papers are directly implementable, 116 are design input. The active library is
139 papers (A/B only; 82 C and 2 D were deleted), with 138 arXiv TeX sources.

---

## 1. The honest starting point

P3.2, P4, and P6 have produced a working instrument but no transfer. The
current facts are:

- Dev is near saturation; the anchor has more headroom, but accepted variants
  have not transferred to fresh tasks.
- The judge is advisory and was measured at kappa 0.0; it must never enter the
  acceptance path.
- The UCB1 bandit has only four arms and ~22 pulls, all with negative mean
  reward. The bottleneck is not the gate; it is proposer diversity and benchmark
  headroom.
- The archive is a greedy hill-climb over one incumbent, which discards
  diversity and makes operator credit assignment noisy.
- Skill memory is currently a flat `HarnessSpec.skills` tuple: no tests, no
  provenance, no admission evidence, no consolidation, no amnesia test.

Therefore P5/P6 must do two things at once:

1. **P5** turn skills and lessons into a verified, bounded, retrievable external
   memory that a frozen 7B can actually use.
2. **P6** turn the single-incumbent loop into a statistically controlled,
   diversity-preserving search that can tell whether an operator or a memory
   policy is working.

Neither is sufficient without a harder benchmark. The roadmap makes benchmark
headroom a parallel workstream, not a later phase.

---

## 2. Shared invariants

These are non-negotiable and stay outside the mutable surface:

- Anchor suite, anchor manifest, acceptance verifiers, governor, sandbox, and
  human promotion gate are immutable.
- No task content leaves the machine; `allow_remote_task_data = false`.
- Memory and skills are **untrusted prompt evidence**, never acceptance
  evidence. Acceptance remains a program verifier.
- Fresh split is never used for selection; it is only a post-acceptance
  confirmation set.
- Every memory/skill promotion has a replayable evidence bundle: verifier
  version, test IDs, run IDs, parent variant, split, and raw scores.
- No embeddings, vector database, or second resident model. Retrieval uses
  SQLite FTS5/BM25 and deterministic token features.
- One generation per daemon session, two evaluator-evolution rungs, and a hard
  token/time budget. Checkpoint after every job.
- All timestamps UTC.

## 3. P5 — process memory

### 3.1 Goal

Make verified experience cumulative without changing model weights:

- **Lessons:** compact, provenance-linked statements about a failure mode and a
  repair strategy.
- **Skills:** named rules with triggers, a rule body, and executable tests,
  admitted only after verifier evidence.
- **Retrieval:** select the few lessons/skills that match the current task and
  failure signature, within a fixed prompt budget.
- **Consolidation:** merge duplicates, promote repeated lessons to skills,
  retire stale or harmful entries, and cap the store.
- **Amnesia test:** prove that memory helps and that removing it hurts, on a
  held-out set that was never used for selection.

### 3.2 What the research supports

- **PYTHALAB-MERA** (`research/10.48550_arXiv.2605.08468/`) is the closest
  blueprint: a frozen model, validation-gated acceptance, episodic memory, AST
  skills, a LinUCB retrieval action, and delayed credit. Adopt the separation
  of generation / control / acceptance, not its full RL stack.
- **Audited Skill-Graph** (`research/10.48550_arXiv.2512.23760/`) supplies the
  audit pattern: skills are promoted only after replay-based verifier evidence;
  evidence bundles are replayable; the verifier is outside the policy runtime.
- **EXG** (`research/10.48550_arXiv.2605.17721/`) supplies the experience-graph
  schema: case nodes (golden/warning), task anchors, similarity edges, and
  correction edges. A SQLite graph is sufficient.
- **ISM** (`research/10.48550_arXiv.2606.31191/`) supplies lifecycle
  mechanisms: audit, merge, prune, promote/demote, reinforce success,
  record anti-patterns, and rehabilitate before pruning—all gated by symbolic
  verification of a frozen model.
- **SkillAxe** (`research/10.48550_arXiv.2606.10546/`) supplies four skill
  quality dimensions: quality impact, trigger precision, instruction
  compliance, and solution-path coverage.
- **SkillRevise** (`research/10.48550_arXiv.2606.01139/`) supplies
  trace-conditioned revision: revise a skill from the execution trace that
  failed, not from a generic critique.
- **Trajectory-Informed Memory** (`research/10.48550_arXiv.2603.10600/`)
  supplies trajectory-to-lesson extraction with provenance and context-aware
  retrieval.
- **Reflexion** (`research/10.48550_arXiv.2303.11366/`) supplies the cheap
  verbal-reflection baseline: store a short lesson, not a transcript.

### 3.3 Data model

Use a separate SQLite database `runs/memory.sqlite3`; do not bloat the variant
archive. WAL mode, foreign keys on, FTS5 virtual tables.

```sql
CREATE TABLE lessons (
  id INTEGER PRIMARY KEY,
  task_id TEXT NOT NULL,
  task_family TEXT NOT NULL,
  failure_signature TEXT NOT NULL,
  trigger_terms TEXT NOT NULL,
  rule TEXT NOT NULL,
  patch_summary TEXT NOT NULL,
  provenance_json TEXT NOT NULL,
  dev_gain REAL,
  anchor_delta REAL,
  fresh_delta REAL,
  success_count INTEGER NOT NULL DEFAULT 0,
  failure_count INTEGER NOT NULL DEFAULT 0,
  status TEXT NOT NULL DEFAULT 'candidate',  -- candidate|verified|quarantined|retired
  created_at TEXT NOT NULL,
  last_used_at TEXT,
  cost_tokens INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE skills (
  id TEXT PRIMARY KEY,                       -- content hash
  name TEXT NOT NULL,
  triggers TEXT NOT NULL,
  rule TEXT NOT NULL,
  tests_json TEXT NOT NULL,
  provenance_json TEXT NOT NULL,
  evidence_json TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'candidate',  -- candidate|verified|quarantined|retired
  version INTEGER NOT NULL DEFAULT 1,
  parent_id TEXT,
  content_hash TEXT NOT NULL,
  created_at TEXT NOT NULL,
  last_used_at TEXT,
  success_count INTEGER NOT NULL DEFAULT 0,
  failure_count INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE skill_edges (
  parent_id TEXT NOT NULL,
  child_id TEXT NOT NULL,
  relation TEXT NOT NULL,                    -- revises|composes|fallback
  PRIMARY KEY (parent_id, child_id, relation)
);

CREATE TABLE evidence (
  id INTEGER PRIMARY KEY,
  subject_kind TEXT NOT NULL,                -- lesson|skill|variant
  subject_id TEXT NOT NULL,
  run_id TEXT NOT NULL,
  variant_hash TEXT,
  split TEXT NOT NULL,                       -- dev|anchor|fresh|memory
  verifier_version TEXT NOT NULL,
  test_ids_json TEXT NOT NULL,
  score_before REAL,
  score_after REAL,
  raw_json TEXT NOT NULL,
  created_at TEXT NOT NULL
);

CREATE VIRTUAL TABLE lesson_fts USING fts5(
  trigger_terms, rule, failure_signature, content='lessons', content_rowid='id'
);
CREATE VIRTUAL TABLE skill_fts USING fts5(
  name, triggers, rule, content='skills', content_rowid='id'
);
```

Add FTS sync triggers in the migration. Store lesson rules at 20–400 chars and
skills at the existing 20–400 char bound; keep the prompt budget bounded.

### 3.4 Retrieval

At task start, build a deterministic state key:

```text
state_key = (task_family, difficulty, failure_signature, attempt_index,
             last_error_type, remaining_attempts)
```

Retrieve:

1. Filter `status='verified'`, matching task family; allow cross-family only
   when the failure signature matches exactly.
2. BM25 over `trigger_terms + failure_signature`.
3. Score:

```text
score = 0.55 * bm25_norm
      + 0.20 * success_rate
      + 0.10 * recency
      + 0.10 * trigger_specificity
      - 0.05 * normalized_cost
```

4. Enforce caps: top 3 skills, top 5 lessons, 1,200 prompt tokens total,
   deduplicated by content hash. If the cap is exceeded, drop the lowest score.
5. Log the selected IDs and scores to `retrieval_events` for later credit
   assignment.
6. Never include the expected outputs, hidden tests, anchor text, or task IDs in
   retrieved text. Run the existing guard on every retrieved rule.

The initial retriever is deterministic BM25. Do **not** add LinUCB or embeddings
until there is enough retrieval evidence and a working memory-eval split. The
bandit can later choose among retrieval policies (`none`, `lesson`, `skill`,
`mixed`) with the same UCB machinery used for operators.

### 3.5 Admission pipeline

A candidate skill or lesson enters the store only through this pipeline:

1. **Static checks:** existing `guard` rules, no task/function names, no anchor
   leakage, no network/subprocess/eval in any skill code, size bounds.
2. **Trigger checks:** new triggers must appear in at least one dev task
   (non-inert) and must not fire on more than 50% of tasks (non-generic).
3. **Executable checks:** every skill carries at least one deterministic test;
   tests run in the sandbox with no network.
4. **Paired dev check:** candidate harness with the new skill vs parent harness
   on the same dev sample; require a positive paired delta or a tie with lower
   cost.
5. **Anchor check:** one-shot on the hidden anchor; reject on regression.
6. **Evidence bundle:** write the verifier version, test IDs, split, raw scores,
   and parent hash to `evidence`; set `status='verified'`.
7. **Quarantine:** any failure sets `quarantined`; quarantined entries are never
   retrieved. A human or a later consolidation run may retire them.

Lessons use the same pipeline, except a lesson may be admitted from a failed
trajectory if it is supported by a successful repair in the same task family and
passes the static/trigger checks.

### 3.6 Consolidation

Run as a passive-daemon job (default every 6 hours, or every 5 accepted
variants):

- **Merge:** Jaccard similarity > 0.80 on trigger terms and rule tokens; keep
  the entry with the strongest evidence; link the merged provenance.
- **Promote:** a lesson becomes a skill candidate after 3 independent successes
  across at least 2 task families, and only if it has a test.
- **Demote/retire:** a skill used at least 10 times with success rate below the
  parent harness, or unused for 20 generations; keep as `retired` for audit.
- **Rehabilitate:** before retiring, try one SkillAxe-style revision using the
  latest failing trace; re-admit only through the full pipeline.
- **Cap:** 200 lessons, 24 skills, 64 MB database; LRU plus evidence score.
- **Rebuild FTS** and `VACUUM` after consolidation.

### 3.7 Amnesia test

Add a hidden, human-signed `memory` split (12 tasks) outside the repo, with its
own manifest, never used for selection. Run:

- `memory=on` vs `memory=off`, same policy model, same temperature 0.
- Metrics: pass@1, repair attempts, tokens, wall time, retrieval count.
- Paired bootstrap CI over tasks (2,000 resamples, CPU only).
- Require a mean pass@1 gain of at least +0.05 with a CI that excludes 0, and no
  anchor regression.
- Run a poisoned-memory variant: inject a malicious/incorrect lesson; the
  admission gate must quarantine it and the amnesia run must not improve.

This is the P5 acceptance test. A memory system that cannot beat `memory=off` on
held-out tasks is not admitted, even if it looks plausible.

### 3.8 Integration points

- `src/janet/harness/spec.py`: add an optional `memory_policy` field
  (`enabled`, `top_k`, `max_tokens`, `min_success`) and include it in
  `content_dict()` so behavior changes are hashed. Bump the seed migration
  path; old hashes remain readable.
- `src/janet/harness/skills.py`: extend `Skill` with `id`, `tests`, `status`,
  `evidence` and keep the existing name/triggers/rule validation.
- `src/janet/loop/generation.py`: retrieve before proposing and before each
  repair attempt; pass selected lessons/skills to the proposer and repair
  prompt; record retrieval IDs in variant details.
- `src/janet/loop/passive.py`: add `memory_consolidate` and `memory_amnesia`
  jobs; gate them on the existing time/budget ladder.
- `src/janet/suites.py`: load the hidden `memory` split via a manifest check.
- New modules: `src/janet/memory/store.py`, `retrieve.py`, `admit.py`,
  `consolidate.py`, `amnesia.py`.
- CLI: `janet memory list|show|verify|consolidate|amnesia`,
  `janet run --memory on|off`.
- Config: `[memory]` with `path`, `top_k`, `max_prompt_tokens`,
  `consolidate_hours`, `max_lessons`, `max_skills`, `amnesia_split`.

### 3.9 Tests and acceptance

Unit/property tests:

- FTS retrieval returns only verified entries and respects the token cap.
- A poisoned skill is quarantined and never retrieved.
- A skill with inert triggers is rejected.
- A skill that names a task is rejected.
- Consolidation merges duplicates and preserves provenance.
- Retired skills are excluded.
- Amnesia test computes a paired CI and fails on a zero-effect store.
- Memory on/off does not change the anchor manifest or acceptance path.
- SQLite migration is idempotent; WAL and FTS triggers work.
- Memory adds <100 ms p95 retrieval and <100 MB RSS.

P5 acceptance evidence:

- Two 10-generation confirmations with memory on (20 total); memory ablation on the hidden split.
- At least one verified skill and one verified lesson admitted with replayable
  evidence.
- Poisoned-memory test blocked.
- No anchor regression; p95 resource compliance.
- A report that states honestly whether memory helped.

## 4. P6 — meta-loop

### 4.1 Goal

Learn which **kind** of change and which **search policy** is working, while
controlling false acceptance and preserving diversity:

- Expand the operator set beyond four arms.
- Replace single-incumbent hill-climb with a bounded frontier.
- Add risk-controlled acceptance (SGM-style) and always-valid fresh release.
- Detect proxy decoupling and stale objectives.
- Report a meta-improvement slope with a bootstrap CI.

### 4.2 What the research supports

- **SGM** (`research/10.48550_arXiv.2510.10232/`) gives the statistical
  acceptance pattern: separate proposal from confirmation; require a
  trajectory-level risk allocation; use an anytime-valid e-process or a
  fixed-sample paired test; protect the verification layer.
- **Always-Valid Inference** (`research/10.48550_arXiv.2605.12947/`) gives the
  release wrapper: a hard-negative reference pool, calibrated p-values, and an
  e-process that controls false release under optional stopping.
- **Polaris** (`research/10.48550_arXiv.2603.23129/`) shows that a small model
  can do experience-abstracted policy repair if failures are generalized into
  compact repair strategies and rendered as minimal patches.
- **Harness Flaws** (`research/10.48550_arXiv.2606.06324/`) gives the
  trace-to-flaw attribution pattern: normalize traces, align steps to harness
  artifacts, consolidate recurring diagnoses, and map them to scoped repair
  operators.
- **GEAR** (`research/10.48550_arXiv.2605.13874/`) gives the bounded frontier:
  elite nodes, parent selection by productivity + local novelty + global
  coverage, mutation and semantic crossover.
- **BenchEvolver** (`research/10.48550_arXiv.2606.01286/`) gives the
  solution-centric task escalation needed to restore headroom.
- **DEI/Heuresis** (`research/10.48550_arXiv.2605.27130/`,
  `research/10.48550_arXiv.2606.25198/`) support diversity and novelty-aware
  selection.
- **Statistical Limits** (`research/10.48550_arXiv.2510.04399/`) and
  **SAHOO** (`research/10.48550_arXiv.2603.06333/`) bound the claims and add
  drift/regression-risk checks.
- **Layered Mutability** (`research/10.48550_arXiv.2604.14717/`) informs
  hysteresis and rollback discipline.

### 4.3 Operator expansion

Start with six arms; do not add more until each has enough pulls:

| Arm | Allowed change | Why |
|---|---|---|
| `prompt` | system prompt only | existing |
| `skill_add` | add one verified skill | separate from revision |
| `skill_revise` | revise one existing skill from a failing trace | SkillRevise/Polaris |
| `budget` | `max_attempts` / `samples_per_attempt` | existing |
| `memory_policy` | retrieval on/off, top-k, min success | P5 coupling |
| `prompt+skill` | prompt + one skill | existing |

Keep operators semantically disjoint; the existing `classify_operator` must
reject a candidate that changes more than its arm permits. Add `stop_rule` and
`routing` only after the first six are stable.

### 4.4 Bandit changes

- Keep UCB1 as the auditable default.
- Add discounted rewards (`gamma=0.98`) or a 50-pull sliding window so the
  policy can adapt to a non-stationary benchmark.
- Add per-task-family arms with shrinkage toward the global mean; a code-repair
  arm may behave differently from an algorithm-design arm.
- Require at least 3 pulls per arm before trusting a mean; untried arms first.
- Record cost (tokens, seconds) per arm; reward is net of a small cost penalty.
- Reward v3:

```text
held-out delta > +0.01: accepted +1.0, rejected +0.5
within ±0.01:           accepted +0.25, rejected 0.0
held-out delta < -0.01: accepted -0.25, rejected -0.5
anchor not measured:    -0.05
proposal error:         -0.25
strict-blocked:         -0.10
cost penalty:           -0.10 * normalized_cost
```

Fresh split remains excluded. The reward is still derived from the gate, never
from model self-report.

### 4.5 Archive and parent selection

Replace `Archive.current()` greedy selection with a frontier:

- Each variant row gains `operator`, `parent2`, `cost`, `novelty`,
  `coverage_cell`, `frontier_status`.
- `frontier` keeps the best variant per MAP-Elites cell:
  `task_family × difficulty_bucket × cost_bucket`.
- Parent selection: 70% exploit (top capability/held-out), 30% explore
  (novelty/coverage); use a small tournament, not a single best.
- Novelty: TF-IDF cosine or token Jaccard between `system_prompt + skills` and
  the archive; no embeddings.
- Semantic crossover: combine a prompt from one elite with a skill from another
  only when the guard passes and the diff is bounded; otherwise mutate.
- Preserve the full lineage and rejected variants for audit.

### 4.6 Statistical acceptance and release

- Use a paired design: candidate and incumbent on the same fixed evaluation
  set; report raw mean difference and a confidence interval.
- For a fixed sample, use a one-sided exact binomial test on paired
  correctness; for optional stopping, use the SGM e-process with a predeclared
  alpha spending schedule.
- Suggested `alpha_total = 0.05`, geometric weights
  `w_g = 0.5^(g+1)` normalized; accept only when the e-value exceeds
  `1/alpha_g` or the fixed-sample p-value is below `alpha_g`.
- Fresh confirmation uses the always-valid release wrapper: build a
  hard-negative pool from prior failures, calibrate p-values, accumulate an
  e-process, and release only when the threshold is crossed.
- A certificate is only valid for the declared evaluation target and verifier
  version; changing the target or verifier requires a new certificate.
- Do not let the fresh split influence selection; it is only a release test.

### 4.7 Decoupling and stale-objective detection

Keep the existing Spearman/half-gain detector and add:

- CUSUM/Page-Hinkley on `dev - heldout` with a small drift (0.01) and threshold
  (0.05); flag when the cumulative gap exceeds the threshold.
- Strict mode: once flagged, require held-out improvement for every acceptance
  until the gap closes for N generations.
- Stale-objective probe: a synthetic shift in the task mix or metric; measure
  detection latency and whether the loop reframes. Record it in the report.
- Fresh rotation: materialize a new fresh split every N generations from a
  pre-authored pool; never use it for selection.

### 4.8 Meta-metrics and dashboard

Add `janet report --meta` (JSON + Markdown):

- `capability(g)`: anchor mean.
- `fresh_capability(g)`: fresh mean after acceptance only.
- `improvement_rate(g)`: capability gain per 1,000 tokens and per 60 seconds.
- `meta_slope`: OLS or Theil-Sen slope of `improvement_rate` over generations;
  2,000-sample bootstrap CI.
- `transfer`: fresh delta vs seed.
- `diversity`: MAP-Elites coverage, distinct operators, task-family spread.
- `integrity`: honest-abstention rate and violations.
- `resource_compliance`: p95 CPU/RAM/VRAM/disk vs the contract.
- Bandit arm table with pulls, mean, cost, discounted mean.
- Memory table with verified/quarantined/retired skills, retrieval hit rate, and
  amnesia result.

### 4.9 Integration points

- `src/janet/harness/bandit.py`: new arms, discounted stats, cost penalty,
  per-family shrinkage, reward v3.
- `src/janet/harness/archive.py`: frontier table/columns, parent selection,
  novelty/coverage, lineage.
- `src/janet/loop/generation.py`: six-arm dispatch; e-process/fixed-sample gate;
  strict mode; cost accounting.
- `src/janet/loop/decoupling.py`: CUSUM and stale-objective probe.
- `src/janet/loop/passive.py`: memory/amnesia jobs; fresh rotation; report.
- `src/janet/loop/confirm.py`: always-valid release wrapper.
- `src/janet/cli.py`: `janet report --meta`, `janet bench rotate-fresh`,
  `janet memory ...`.
- `configs/default.toml`: `[meta]` alpha, weights, discount, frontier size,
  freshness intervals; `[memory]`.

### 4.10 Tests and acceptance

- UCB1 chooses untried arms first, is deterministic on ties, and handles cost.
- Reward v3 is monotone in held-out delta and never uses fresh.
- E-process/fixed-sample gate rejects a null candidate and accepts a strong
  paired improvement on synthetic data.
- Alpha spending cannot exceed the total.
- Frontier preserves at least one variant per occupied cell; parent selection
  covers exploit and explore.
- CUSUM flags a synthetic dev-anchor gap within the declared latency.
- Stale-objective probe is detected and reported.
- Fresh rotation never leaks into selection.
- Meta-slope CI is computed on synthetic data with a known slope.
- Two 10-generation confirmations (20 total), p95 resource compliance, no anchor
  regression, and at least one accepted variant surviving rollback.

## 7. Risks and kill criteria

| Risk | Mitigation | Kill criterion |
|---|---|---|
| Memory overfits dev | hidden memory split; admission evidence; amnesia test | memory-on fails to beat memory-off |
| Poisoned skill | quarantine, replay evidence, static audit | any quarantined skill retrieved |
| Retrieval prompt bloat | 1,200-token cap; top-k; dedupe | p95 prompt > cap or latency >100 ms |
| Bandit overfits 22 pulls | min pulls, discounting, per-family shrinkage | no arm separation after two 10-generation runs |
| False acceptance | e-process/fixed-sample, alpha spending, anchor | any accepted non-improving synthetic candidate |
| Diversity collapse | frontier, novelty, MAP-Elites | one lineage >70% of frontier |
| Benchmark saturation | BenchEvolver-style escalation, fresh rotation | one-shot baseline >0.9 with no held-out gain |
| Resource spike | one model, one generation, early stop | p95 above contract for 3 sessions |
| Meta-slope noise | bootstrap CI, two 10-generation runs | CI includes 0; report as negative |

If P5 fails the amnesia test, stop P5 and do not promote memory. If P6 cannot
separate operators after two 10-generation runs, the bottleneck is the proposer or the
benchmark, not the bandit; move effort to benchmark headroom and mutation
diversity rather than adding more arms.
